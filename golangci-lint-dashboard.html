01 — Layers

System Architecture

Core Idea က golangci-lint ကို request path ပြင်ပမှာ Run စေပြီး, Web UI ဟာ Job တစ်ခု Trigger လုပ်ပြီး Poll/Subscribe လုပ်တဲ့ Control Plane အဖြစ်ပဲ ရှိသင့်ပါတယ်။ Lint Run တစ်ခုဟာ Repo အရွယ်အစားပေါ်မူတည်ပြီး စက္ကန့်ပေါင်းများစွာ ကြာနိုင်တာမို့, Synchronous HTTP Request ထဲမှာ Block လုပ်ထားလို့ မဖြစ်ပါဘူး။

Scalability အတွက် အခြေခံဆုံးဖြတ်ချက်

Scan Runner ကို API Process အတွင်းမှာ Spawn မလုပ်ဘဲ, Job Queue (Redis) နောက်ကွယ်က Worker Fleet အဖြစ် ခွဲထားတာက Repo အရေအတွက် များလာလည်း, Repo အရွယ်အစား ကြီးလာလည်း, Worker Instance အရေအတွက်ကိုပဲ တိုးချဲ့ရင် ရပါတယ် — API/UI Layer ကို ထိခိုက်စေဘူး။

  • Monorepo support — Configuration entity ကို repo_ref + subpath level အထိ Scope ချထားပြီး, Package အလိုက် သီးခြား Scan/Plan လုပ်နိုင်အောင် ဒီဇိုင်းလုပ်ထားပါတယ်.
  • Incremental scan — golangci-lint ရဲ့ --new-from-rev Flag ကို default အဖြစ် သုံးပြီး, Full Repo မဟုတ်ဘဲ Diff-only Issue တွေကိုပဲ ဦးစားပေး ဖော်ပြပါမယ် (Full Scan ကို Manual Trigger သီးခြား ထားပါတယ်).
  • Per-repo lock — Redis-based Distributed Lock နဲ့ Repo/Branch တစ်ခုချင်းစီအတွက် Scan/Fix တစ်ခုတည်းသာ တစ်ချိန်တည်း Run ခွင့်ပြုထားပါတယ် (Concurrency Risk အသေးစိတ်ကို Risks အပိုင်းမှာ ဖော်ပြပါမယ်).

Security posture — Architecture level

Fix Service ကလွဲရင် ကျန်တဲ့ Service အားလုံးက Git Remote ကို တိုက်ရိုက် Access မလုပ်ပါဘူး။ Fix Service ကိုယ်တိုင်ကလည်း lint-fix/* Branch Prefix အောက်မှာပဲ Commit ခွင့်ရှိပြီး, main/master ကို တိုက်ရိုက် Write လုပ်ခွင့် လုံးဝမရှိပါဘူး — Human Reviewer က PR/MR အနေနဲ့ ခွင့်ပြုမှသာ Merge ဖြစ်ပါမယ်။ Component-level Security Control (Approval Gate, Permission, Audit Log) တွေကို Component Responsibilities မှာ အသေးစိတ် ဖော်ပြပါမယ်။

02 — End to end

Workflow

User Interaction တစ်ခုချင်းစီရဲ့ နောက်ကွယ်မှာ ဘယ် Service က ဘာ Trigger လုပ်လဲဆိုတာကို Sequence Diagram နဲ့ ဖော်ပြပါမယ်။ Scan → Plan → Fix → Re-scan ဆိုတဲ့ Loop ဟာ Design ရဲ့ ဗဟိုချက်ပါ။

Issue state machine

LintIssue တစ်ခုချင်းစီရဲ့ Lifecycle ကို Explicit State အဖြစ် သိမ်းထားပါတယ် — UI ရဲ့ Status Column နဲ့ တိုက်ရိုက် Map ဖြစ်ပါတယ်.

open → planned → fix_applied → resolved (or reopened)
%%{init: {'theme':'neutral'}}%%
stateDiagram-v2
  [*] --> open
  open --> planned: Plan generated
  planned --> fix_applied: Fix approved + applied
  fix_applied --> resolved: Re-scan confirms issue gone
  fix_applied --> reopened: Re-scan still detects it

03 — REST surface

API Design

Scan/Fix ဟာ ကြာချိန်ရှည်တဲ့ Operation တွေမို့ POST Endpoint အများစုက 202 Accepted ပြန်ပြီး, Client က Poll (သို့) Server-Sent Events နဲ့ Progress ကို လိုက်ကြည့်ရပါတယ်။

04 — Entities

Database Design

golangci-lint ရဲ့ Native JSON Output မှာ Severity Field ဟာ Config မထည့်ရင် အလွတ်ချည်းသာ ရှိတတ်ပါတယ် — ဒါကြောင့် Parser Service အနီးမှာ Linter → Severity Mapping ကို Config Entity ထဲမှာ ခွဲထားပါတယ် (ဒီ Repo ရဲ့ root_cause_mappings.json ပုံစံအတိုင်း Config-driven Mapping ကို ဆက်ခံသုံးထားတာပါ).

Notable fields

  • LintIssue.fingerprint — hash(file_path + rule + normalized_message); Scan အသစ်တစ်ခုချင်းစီမှာ Issue တူ/မတူ Track လုပ်ဖို့ (Line Number ပြောင်းသွားလည်း Track ဆက်ရအောင်).
  • FixPlan ↔ LintIssue Junction Table — Plan တစ်ခုက Issue များစွာကို Batch အနေနဲ့ ကိုင်တွယ်နိုင်အောင် (ဥပမာ File တစ်ခုတည်းက Issue 3 ခု).
  • Configuration.scope — global (Default Severity Map, Model Choice) vs repo (Repo-specific golangci-lint config path, Permission Override).
  • Org ရဲ့ Existing Stack (GORM + MySQL, git.frontiir.net/sa-dev/rtdatacore Pattern) ကို ဆက်လက် Reuse လုပ်ဖို့ အကြံပြုပါတယ် — Team အတွက် Operational Overhead အနည်းဆုံးဖြစ်မှာပါ.

06 — Services & controls

Component Responsibilities

Service ခြောက်ခုကို Single Responsibility အလိုက် ခွဲထားပြီး, Fix Service တစ်ခုတည်းကသာ Git Write Access ရှိပါတယ်.

Service breakdown
ServiceResponsibilityDepends on
Scan ServiceChecks out an isolated worktree, runs golangci-lint run --out-format json, tracks scan statusJob queue, Runner
Parser ServiceNormalizes raw JSON → LintIssue rows; applies severity-mapping config; computes fingerprintConfiguration
Plan ServiceBuilds the AI prompt (rule + source context + repo conventions), calls Claude, caches plan by fingerprintAI Layer, LintIssue
Fix ServiceApplies native --fix for autofixable linters; applies AI-authored patch for the rest; commits only to lint-fix/*Git, Scan Service (rescan)
History ServiceAppend-only audit read model over scans, fixes, rollbacksStorage
Rollback ServiceReverts a FixHistory entry via git revert (never reset/force-push), triggers confirmation rescanGit, Scan Service

Security controls, mapped to component

Confirmation · Approval · Permission · Audit log
ControlWhere enforcedBehavior
ConfirmationUI + API GatewayTyped/explicit confirm required when risk = High or breaking_change = true
ApprovalPlan ServiceFixPlan.status must be approved (approver id + timestamp) before Fix Service accepts the request — enforced server-side, not hidden by UI alone
Permission (RBAC)API Gatewayviewer / approver / operator / admin roles, same ACL shape as this org's existing api_key_permissions.json convention
Audit logHistory ServiceEvery approve/apply/rollback writes an immutable entry (actor, before/after, timestamp) — separate from mutable status fields

Recommended folder structure

golangci/ — one package per responsibility
golangci/ ├── api/ ← Gin handlers, request validation, RBAC middleware ├── scanner/ ← golangci-lint process orchestration, worktree lifecycle ├── parser/ ← JSON → LintIssue normalization, severity mapping ├── planner/ ← AI Layer client, prompt templates, plan cache ├── fixer/ ← autofix + AI patch application, git branch/commit ops ├── history/ ← scan/fix/rollback audit read models ├── worker/ ← job queue consumer — separate scalable process (added: see §Scalability) ├── storage/ ← GORM models + migrations ├── ui/ ← SPA — dashboard, issue list, plan viewer, history └── config/ ← severity-mapping.json, permissions.json, model-config.json

worker/ ကို User ရဲ့ မူလ List ထဲမှာ မပါခဲ့ပါဘူး — Scan/Fix Job တွေကို API Process ထဲက ခွဲထုတ်ဖို့ လိုအပ်တဲ့အတွက် Senior-level Recommendation အနေနဲ့ ထပ်ဖြည့်ထားတာပါ (§ Scalability ကို ရည်ညွှန်းပါတယ်).

07 — What could go wrong

Risks

Risk register
CategoryRiskMitigation
ArchitectureScan Runner coupled to API process blocks horizontal scalingSeparate worker pool behind a job queue (see §Scalability)
PerformanceLarge monorepo scan takes minutes, blocks the UI thread of thoughtAsync scan + polling/SSE; --new-from-rev incremental scans by default
ConcurrencyTwo fixes race on the same file/branchRedis-based per-repo/branch lock; serialized fix queue
AI wrong fixLLM proposes a plausible but behavior-changing patchMandatory human approval gate; automatic rescan diff; block apply if severity count increases
AI wrong fixNon-deterministic AI output across identical inputsCache plan by issue+source fingerprint; store model + prompt version on FixPlan
RollbackRevert conflicts with later commits on the same branchRollback only via git revert, never reset/force-push; surface manual-resolution state instead of forcing
SecurityFix Service granted overly broad repo write accessCredentials scoped to lint-fix/* branch prefix via branch protection; never main
08 — Beyond v1

Future Enhancements

  • SARIF export — GitHub/GitLab Code Scanning integration အတွက် Parser Service ကနေ SARIF Format ကို ထုတ်ပေးနိုင်အောင်.
  • PR/MR bot mode — Plan ကို PR Comment အနေနဲ့ တင်ပြီး, Approval ကို PR Review Workflow ထဲကနေပဲ လုပ်နိုင်အောင် (သီးခြား UI မလို).
  • Pluggable linters — Parser Service ကို Linter-output-format အလိုက် Plugin ခွဲထားပြီး, Go အပြင် eslint/ruff စတာတွေအထိ Support ချဲ့ခြင်း.
  • AI cost guardrail — Scan တစ်ခုမှာ Plan Request အများဆုံးအရေအတွက် Cap ချခြင်း; Autofixable Issue တွေကို AI ခေါ်စရာ လုံးဝမလိုအောင် Native --fix ကို ဦးစားပေးခြင်း (ဒါက Cost/Risk နှစ်ခုလုံးကို လျှော့ချပေးပါတယ်).
  • Trend analytics — Linter/Severity အလိုက် အချိန်နဲ့အမျှ Issue ရေအတိမ်ရေနက် ပြောင်းလဲမှု Dashboard.
